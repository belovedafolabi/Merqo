# Per-Client Deployment Provisioning

Merqo's codebase is identical across every client. A new client deployment
differs only in configuration: its own Supabase project, its own Vercel
deployment, its own environment values. This is the documented, repeatable
process for standing one up — the thing `docs/TAS.md` §44/§48–49 flags as a
deliberate concern not to be solved ad hoc at the first real launch.

The automation is matched to the near-term client count (a handful). The
error-prone, order-dependent database half is scripted; project creation is
six dashboard steps.

## Scripted vs. manual — the split

### Manual (dashboard, ~6 steps)

1. **Create the Supabase project** — pick a region near the client, set a
   strong database password (record it in the client's Vercel env as
   `SUPABASE_DB_PASSWORD`, server-only). This is what provides the
   `auth` / `storage` / `extensions` schemas that migrations build on top of.
2. **Create the Vercel project** — link the `belovedafolabi/Merqo` repo,
   Production branch `main`.
3. **Set the Vercel environment variables** (Production + Preview) — the list
   `provision-client.sh` prints, split into per-client and platform-shared
   below.
4. **Attach the client's custom domain** in Vercel, set `NEXT_PUBLIC_APP_URL`
   to it.
5. **Register the Paystack webhook**: `https://<domain>/api/webhooks/paystack`
   (see `README.md` "Paystack webhook + the daily subscription cron").
6. **Create the UptimeRobot monitor** — see `operations.md`.

**Rejected as automation:** scripting steps 1–2 via the Supabase Management
API and Vercel CLI. It requires storing and rotating two long-lived
platform-owner tokens to replace roughly six clicks performed a few times a
year — a worse security posture for negative operational value at this client
count.

### Scripted (`scripts/provision-client.sh`)

```bash
# Against the new project (links it first; needs SUPABASE_DB_PASSWORD in env):
SUPABASE_DB_PASSWORD=... pnpm client:provision --project-ref <newref>

# Or a direct connection string:
pnpm client:provision --db-url "postgresql://postgres:...@db.<newref>.supabase.co:5432/postgres"
```

What it does, in order:

1. **Preflight** — the Supabase CLI version matches the pin in
   `package.json`; the target is reachable; the target's `public` schema is
   **empty** (it refuses a populated one and points you at
   `migrate-client.sh`).
2. **`supabase db push`** — applies all migrations.
3. **`supabase/seed.sql`, explicitly.** This is the trap the script exists to
   remove: `supabase db push` does **not** run the seed against a
   linked/remote project (only `db reset` does, and `db reset` against a
   client would be catastrophic). A hand-provisioned client would silently
   get no business types, no roles, no permissions, no subscription pricing.
   `seed.sql` is `on conflict do nothing` throughout, so re-running is safe.
4. **`verify-client-db.sql`** — RLS enabled on every public table, ≥1 policy
   (except the two policyless-by-design tables), seed catalog counts,
   `roles_org_scope_check` present. Fails loudly.
5. **Migration ledger check** — `schema_migrations` row count vs. the repo's
   `supabase/migrations/*.sql` count.
6. **Generates this client's `CRON_SECRET`** (`openssl rand -hex 32`), prints
   it once, never writes it to disk, and prints its fingerprint for the
   register.

## Recorded local proof

Run 2026-09-01 against a fresh local database seeded only with the Supabase
base schemas (`auth`, `storage`, `extensions`, `graphql`) and an empty
`public`:

```

    supabase CLI 2.115.0 (matches pin)
    target reachable, public schema empty
==> Applying migrations (supabase db push)      [151 migrations]
==> Seeding (supabase/seed.sql)
==> Verifying
    DO                                          [verify-client-db.sql passed]
    migrations applied: 151 (repo has 151)
==> PROVISIONING COMPLETE                        [CRON_SECRET + fingerprints printed]
```

Spot-check of the provisioned database: 13 business types, 8 system roles, 59
permissions, `roles.organization_id` column present.

The empty-schema guard was confirmed to refuse a populated target:
`! target public schema already has 50 tables — not empty, refusing`.

**Handed to the operator** (not doable from this repo): creating the real
Supabase project and Vercel project, and setting the env vars — the six
manual steps above.

## Per-client secret freshness

Enforced two ways:

- **By construction.** `CRON_SECRET` is *generated by the script*, never
  accepted as input — reuse is impossible. Every Supabase-issued value
  (project URL, anon key, service-role key, DB password) is per-project by
  construction; there is nothing to reuse unless a human copy-pastes.
- **By verification.** The script prints `sha256(value)` truncated to 12 hex
  characters for `SUPABASE_SERVICE_ROLE_KEY` and `CRON_SECRET`. Record them in
  the register below. If a fingerprint already appears, a secret was reused —
  stop and regenerate. (A truncated one-way hash is not a secret and is safe
  in a public repo.)

### Per-client vs. platform-shared values

| Per-client (unique per deployment) | Platform-shared (identical everywhere) |
|------------------------------------|----------------------------------------|
| `NEXT_PUBLIC_SUPABASE_URL` | `RESEND_API_KEY` — the platform's sending domain |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | `PAYSTACK_SECRET_KEY` — bills the *platform owner's* subscription revenue; Paystack is subscription billing only, never POS payments |
| `SUPABASE_SERVICE_ROLE_KEY` | |
| `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD` | |
| `NEXT_PUBLIC_APP_URL` | |
| `CRON_SECRET` | |

A naive reading of "no key reuse across clients" would say generate a fresh
Paystack key per client. That is wrong: `PAYSTACK_SECRET_KEY` and
`RESEND_API_KEY` are platform-owned and correctly identical across every
client.

## Migration rollout across the fleet

Once a client is live, apply new migrations with:

```bash
SUPABASE_DB_PASSWORD=... pnpm client:migrate --project-ref <ref> --backup-taken
```

`migrate-client.sh` is deliberately a separate script from provisioning: it
never re-seeds and never touches secrets. It refuses to run without
`--backup-taken` (you ran `scripts/backup.sh` against this client first),
shows the pending migration list and asks for confirmation, applies, then
re-runs `verify-client-db.sql`.

**Rollout rule: migrations must stay backward-compatible for one release.**
Vercel's deploy and Supabase's migration are not atomic, and the fleet is
updated one client at a time — so for the window between "migration applied"
and "new code deployed", the *old* code must still work against the *new*
schema. A column rename becomes add-new + backfill + (next release)
drop-old.
